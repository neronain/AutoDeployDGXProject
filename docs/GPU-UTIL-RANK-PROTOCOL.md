## 0 · ข้อเท็จจริงที่ต้องอ่านก่อน — **เรารัน TP8 ไม่ได้**

ข้อขัดแย้งอยู่ที่ TP8 แต่ recon ของเราเอง (`docs/HCA-DUAL-TEST.md` §3 · read-only 2026-09-20)
บอกว่า **ฟลีตเราทำ TP8 ไม่ได้ ไม่ใช่แค่วันนี้ แต่ด้วยสายที่มีอยู่**:

| | |
|---|---|
| เครื่องที่ reachable | 11 |
| มี ConnectX-7 เลย | **5** |
| ต่อสายถึงกันเป็นคู่ | **2 คู่** — `msi-1`↔`msi-2` · `gigabyte01`↔`gigabyte02` |
| มี ConnectX แต่ไม่มีสาย | `msi-5` |
| GB10 ที่ **ไม่มี ConnectX เลย** | `spark-01..04` · `dgx-msi` — `/sys/class/infiniband/` ว่าง |

**world size สูงสุดบน fabric เดียวของเราคือ 2** · สองคู่นั้นเป็นเกาะคนละเกาะ ไม่ได้ต่อถึงกัน ·
ตัวเลข "16 เครื่อง · 688 GB" ใน `README.md` นับทุกเครื่องในทะเบียนรวม RTX และเครื่องที่ไม่มี fabric
— **ไม่ใช่ 16 เครื่องที่ stacked ด้วยกันได้**

> ถ้าข้อนี้ผิด (มี switch · ย้ายสายได้ · มีเครื่องที่ recon ไม่เห็น) **บอกก่อนรัน** แล้วเติม arm
> `N=4` / `N=8` เข้าไป — สคริปต์รับ `--arm NAME:SLUG:N` ที่ N เท่าไรก็ได้ · โปรโตคอลนี้ออกแบบให้
> **ขยายขึ้นได้ ไม่ใช่ผูกกับ N=2**

**ผลที่ตามมา: คำถามในบรีฟ ("0.75 หรือ 0.80 ถูกที่ TP8") ตอบด้วยฟลีตนี้ไม่ได้ ไม่ว่าจะออกแบบดีแค่ไหน**
§1 จึงเปลี่ยนคำถามเป็นคำถามที่ตอบได้ **และมีค่ากับ `fit` มากกว่า**

## 1 · คำถามที่การวัดนี้ตอบ — ประโยคเดียว ตรวจสอบได้

> **หน่วยความจำที่เอนจินใช้ไปนอกงบที่ vLLM คิดว่าตัวเองคุม (`X`) โตตามจำนวน rank,
> โตตาม checkpoint, หรือไม่โตตามอะไรเลย?**

ทำไมนี่คือคำถามที่ถูก: ตัวเลข 0.75 / 0.80 **ไม่ใช่ค่าคงที่ของฮาร์ดแวร์** มันคือผลหาร

```
gpu_util_max  =  (MemTotal − X − safety) / MemTotal
```

ใครก็ตามที่รายงาน "0.75 ที่ TP8" กำลังรายงาน `X` ของเขาโดยไม่รู้ตัว · **ถ้าเรารู้ `X` และรู้ว่ามันขึ้นกับอะไร
เราไม่ต้องเถียงเรื่อง 0.75 กับ 0.80 อีกเลย — เราคำนวณมันได้** และนั่นคือสิ่งที่ `fit/sizing.py` ต้องการ
ไม่ใช่ตัวเลขเดี่ยว ๆ สองตัว

### `X` วัดได้จริง ไม่ต้องเดา

DGX Spark เป็น **unified memory** — มี pool เดียว และ `/proc/meminfo` เห็นทั้งหมด (ต่างจากการ์ดแยก
ที่ต้องถาม NVML ซึ่ง §1 ของ field notes บอกว่าไม่รองรับ unified) ฉะนั้นต่อเครื่อง:

```
X = (used ตอน serving) − (used ตอน idle) − (Model loading took + Available KV cache memory)
```

สองพจน์หลังคือตัวเลข **GiB** ที่ vLLM พิมพ์เอง — ไม่ใช่จำนวน token
(`docs/DGX-SPARK-VLLM-FIELD-NOTES.md` §11: vLLM พิมพ์ `max_concurrency × max_model_len`
ซึ่งกระโดดตาม `--max-model-len` ทั้งที่หน่วยความจำเท่าเดิม · สคริปต์เก็บค่า token ไว้ใต้คีย์
`kv_cache_tokens_DO_NOT_USE` เพื่อให้ชัดว่ามันไม่ใช่ตัวตัดสิน)

สมมติฐานสามข้อทำนายคนละอย่าง **และแยกกันได้ด้วยการวัด**:

| | กลไก | ทำนายว่า |
|---|---|---|
| **H_rank** | NCCL จองต่อ rank (เรื่องที่ README อ้าง) | `X(2) − X(1)` ต่างชัด · `X(1)` เล็ก |
| **H_ckpt** | COW break ตอนโหลด MoE (§1.7 R8 · ~27 GiB/rank) | `X(1)` **ใหญ่อยู่แล้ว** · ต่างตาม checkpoint ไม่ใช่ตาม N |
| **H_host** | เพดานคือ host headroom เฉย ๆ | `X` ใหญ่แต่ **แบน** ทุก arm |

> **ข้อสังเกตที่เป็นหัวใจ**: ตัวเลข "~24 GiB ต่อ rank" ที่ README อ้างว่าเป็น NCCL อยู่ใกล้
> **~27 GiB/rank** ที่ §1.7 R8 วินิจฉัยว่าเป็น COW break ของ fused-MoE expert copy มาก ·
> สองอันนี้เป็นคนละกลไกโดยสิ้นเชิง และ **แยกออกได้ที่ N=1 ซึ่งไม่มี NCCL อยู่ในโปรเซสเลย**

## 2 · การเลือกโมเดล — เหตุผลที่กลับหัวกับสัญชาตญาณ

สัญชาตญาณคือ "เอา DeepSeek-V4.1-Flash ไปรัน TP8 แล้วดู" · **นั่นคือวิธีที่ผิด แม้จะมีเครื่องพอ**

**ข้อขัดแย้งอยู่ระหว่างโมเดลสองตัวคนละขนาด** (DeepSeek-V4.1-Flash → 0.75 · GLM-5.3 → 0.80)
ทั้งคู่ที่ TP8 เหมือนกัน · แปลว่าตัวแปรที่ต่างกันจริง ๆ **ไม่ใช่ N — มันคือโมเดล**
การเอาโมเดลใดโมเดลหนึ่งไปรันที่ TP8 จึง **ทำซ้ำ confound เดิม** ไม่ได้ตัดสินอะไร
(นี่คือความผิดพลาดแบบเดียวกับ §10 ที่รีโปต้นทางเปลี่ยน gmu 0.78→0.80 *และ* เปิด tools/vision
พร้อมกัน แล้วยกผลให้ clock latch)

**ทางเดียวที่แยก "ผลของ N" ออกจาก "ผลของโมเดล" ได้คือตรึงโมเดล แล้วขยับ N ทีละขั้น**
และการตรึงโมเดลข้าม N บังคับให้โมเดลนั้น **ต้องลงเครื่องเดียวได้ที่ N=1** — ซึ่ง
**โมเดลที่ขัดกันทั้งสองตัวทำไม่ได้ทั้งคู่** จึงใช้เป็นเครื่องมือวัดไม่ได้ทั้งคู่

เพิ่มอีกสองข้อห้ามจากเอกสารเราเอง:
- **R8** (`docs/UPGRADE-2026-09.md` §1.7): `nvidia/DeepSeek-V4.1-Flash-NVFP4` = **ห้าม deploy** —
  14 boot บน 4× GB10 ไม่เคย serve สำเร็จ · เครื่องโดน watchdog reset ไม่ใช่ OOM kill
- **stacked ต้องเป็น safetensors** (`RUNBOOK-MULTI-NODE.md`) — GGUF ตัดออกทั้งหมด

### เครื่องมือวัดที่เลือก

| arm | โมเดล | N | ทำไมตัวนี้ |
|---|---|---|---|
| **M1** | `Qwen3.5-122B-A10B-abliterated-NVFP4` (MoE · NVFP4 · safetensors) | 1 | **เซลล์ที่คุ้มที่สุดในทั้งโปรโตคอล** — hardware-validated บน DGX Spark เครื่องเดียวของเราเองแล้ว (`ROADMAP.md` 2026-08-02 · ctx 65,536 · weights โหลดจริง 69.62 GiB) · **ที่ N=1 ไม่มี NCCL ในโปรเซสเลย** ถ้า `X` ยังใหญ่ → "24 GiB/rank เป็นของ NCCL" ตายทันที โดยไม่ต้องเทียบกับอะไร · ใช้ **1 เครื่อง ไม่ต้องมีสาย** |
| **D1** | dense safetensors เล็ก (`Qwen/Qwen3-8B` — vLLM-validated `ROADMAP.md` 2026-08-03) | 1 | control ของแกน checkpoint · dense ไม่มี fused-MoE expert copy จึงไม่มี COW break |
| **D2** | **ตัวเดียวกับ D1** | 2 | แกน rank · **ต่างจาก D1 แค่จำนวนเครื่อง** ตัวเดียวเท่านั้น |

**ทำไมเครื่องมือวัดถึงเป็นโมเดล *เล็ก*** — `X` วัดเป็น **ผลต่าง** · weights ที่ใหญ่ไม่เพิ่มสัญญาณให้ผลต่างเลย
มีแต่กินหัวเครื่องที่เรากำลังจะวัด เพิ่มความเสี่ยง OOM และเพิ่มเวลา load ต่อเซลล์หลายเท่า ·
ถ้า `X(2) − X(1)` ยังโผล่ **แม้กับโมเดล 8B** นั่นคือ NCCL แน่นอน เพราะ buffer ของ NCCL
เป็นฟังก์ชันของ `NCCL_BUFFSIZE × channels × peers` ไม่ใช่ของขนาดโมเดล

**โมเดลต้องอยู่บนเครื่องแล้ว** — รัน `lmds node run <node> scan` ก่อนเสมอ
(`RUNBOOK-MULTI-NODE.md` §1) · ถ้าต้องโหลดใหม่ เวลารวมบานจากชั่วโมงเป็นครึ่งวัน ·
ถ้า slug ที่มีอยู่ไม่ตรงกับข้างบน **ให้สลับได้** ตามเกณฑ์นี้ ซึ่งเป็นเกณฑ์ที่แท้จริง ไม่ใช่ชื่อรุ่น:
D = dense · safetensors · ลงเครื่องเดียวได้สบายที่ gpu-util 0.70 · M = MoE + quant
· safetensors · ลงเครื่องเดียวได้ · **ไม่ใช่** NVFP4-MoE ที่ใหญ่จนต้อง TP (ข้อห้าม R8)

## 3 · รันอะไร ที่ไหน กี่เครื่อง นานแค่ไหน

**`drive` รันบน LMDS hub ที่เป็นเจ้าของ node พวกนั้น** — เครื่องที่พิมพ์ `lmds node ctl <node> ...`
แล้วผ่านอยู่แล้ว (ฟลีตจริง = `Autodeploy` · `docs/FLEET-STATE.md`) · **รันจาก MacBook ไม่ได้**
เพราะไม่มี SSH ถึงฟลีต · subcommand ที่เหลือรันบน node และถูกส่งผ่าน `python3 -` ทาง stdin —
**ไม่ติดตั้งอะไรบนเครื่องปลายทางเลย** (สำนวนเดียวกับ `scripts/hca_ab_bench.py`)

### Phase 0 — 1 เครื่อง ไม่ต้องมีสาย · ~1 ชม.

```bash
lmds node run msi-1 scan              # weights อยู่ครบไหม ก่อนอื่นเลย

  --arm D1:<dense-slug>:1 --arm M1:<moe-slug>:1 \
  --node-order msi-1 --gpu-util 0.70 --repeats 3        # ดูแผนก่อน ไม่แตะอะไร

python3 scripts/gpu_util_rank_probe.py drive \
  --arm D1:<dense-slug>:1 --arm M1:<moe-slug>:1 \
  --node-order msi-1 --ssh-target msi-1=<user>@<ip> \
  --gpu-util 0.70 --repeats 3 --out docs/evidence/gpu-util-rank/
```

6 เซลล์ × ~8 นาที + preflight ~20 นาที ≈ **1 ชั่วโมง บนเครื่องเดียว**
**Phase 0 อาจจบเรื่องได้เลย** ถ้า `X(N=1) ≥ 15 GiB` (ดู §5 ข้อ falsification)

### Phase 1 — 2 เครื่อง (คู่ที่ต่อสายแล้ว) · ~1.5 ชม.

```bash
python3 scripts/gpu_util_rank_probe.py drive \
  --arm D1:<dense-slug>:1 --arm D2:<dense-slug>:2 --arm M1:<moe-slug>:1 \
```

**ใช้ 2 เครื่อง ไม่ใช่ 16 · ~3 ชั่วโมงของ GPU** (ถ้า weights อยู่ครบแล้ว) ·
อีก 14 เครื่องทำงานตามปกติตลอด · **ไม่มีการหยุดโมเดลของใครทั้งสิ้น**

## 4 · กันตัวแปรปน — สิ่งที่สคริปต์บังคับ และจุดที่มันยอมหยุด

> §10 ของ field notes: clock latch ทำให้ตัวเลขทุกตัวโกหกได้ · และรีโปต้นทางเองก็เปลี่ยนสองอย่าง
> พร้อมกันแล้วยกผลให้อย่างเดียว · **อย่าทำพลาดแบบเดียวกัน**

1. **`--gpu-util` ตรึงทุกเซลล์ ไม่มีการ sweep หา OOM เลย** — การไล่ให้มัน OOM คือสิ่งที่รีโปต้นทางทำ
   และมันแยก "พังตรงไหน" ออกจาก "พังเพราะอะไร" ไม่ได้ · เราวัด `X` แล้ว **คำนวณ** เพดานออกมา
   (ผลพลอยได้: ไม่ต้องทำเครื่องตายซ้ำ ๆ)
2. **ต่างกันตัวเดียวต่อเซลล์** — arm คือคู่ `(checkpoint, N)` · D1→D2 ต่างแค่ N · D1→M1 ต่างแค่ checkpoint ·
   image / context / prompt / gpu-util เหมือนกันหมด
3. **burn gate ก่อนและหลัง** ทุกเครื่อง (§10) · **สคริปต์นี้ไม่ได้เขียน burn เอง** — เป็นของทีม burn-gate ·
   ตอนนี้ default ชี้ไปที่ `scripts/hca_ab_bench.py burn` ที่มีอยู่แล้ว · **เมื่อ `lmds burn` ออก ให้ชี้
   `--burn-cmd` ไปที่นั้น** · burn ไม่ผ่าน = **ABORT ไม่ใช่ warning** · latch ระหว่างทาง = ทั้ง session เป็นโมฆะ
4. **interleave + หมุนลำดับทุกรอบ** (`D2 M1 D1` · `M1 D1 D2` · `D1 D2 M1`) — ไม่ใช่ `D1 D1 D1 · D2 D2 D2` ·
   เครื่องที่ร้อนขึ้น drift หรือ latch กลางทางจะแสดงตัวเป็น "ผลของ arm" ถ้าเรียงเป็นบล็อก
5. **A-B-A บน idle baseline** — วัด idle ก่อนและหลังทั้ง session · ต่างกันเกิน **2.0 GiB** = session drift
   → `INVALID` · ทิ้งแล้วรันใหม่
6. **≥3 รอบต่อ arm** · รายงาน median/min/max **ไม่เคยรายงาน mean เปล่า** · ถ้า spread ในกลุ่มใหญ่กว่า
   ผลต่างระหว่างกลุ่ม → ผลเป็น `INCONCLUSIVE` ไม่ว่า median จะสวยแค่ไหน
   (`docs/UPGRADE-2026-09.md`: prefill spread 33.7% ใหญ่กว่าผลของ config ส่วนใหญ่)
7. **วัดสองทางแล้วบังคับให้ตรงกัน** — `x_accounted` (จากบรรทัดที่ vLLM พิมพ์) กับ `x_budget`
   (จาก `gpu_util × MemTotal`) · ต่างเกิน 3 GiB = เซลล์ถูกติดธง ไม่ใช่เฉลี่ยเงียบ ๆ

### สคริปต์หยุดเองเมื่อไร (ไม่ยอมให้ตัวเลขสวย ๆ ออกมา)

| เงื่อนไข | ทำอะไร |
|---|---|
| burn gate fail เครื่องใดเครื่องหนึ่ง | **ABORT** ก่อนเริ่ม · หลังจบ = `verdict: INVALID` |
| node ไม่ว่าง (มี container / GPU app / โปรเซส vLLM ค้าง) | **ABORT** — และ **ไม่หยุดของใครทั้งนั้น** ให้คนตัดสินใจ |
| node อยู่ใน deny list (`dgx-70` เป็นค่าตั้งต้น) | **ABORT** ทันทีตั้งแต่ก่อนแตะ ssh |
| `network-info` ไม่มี NCCL if หรือ HCA (N≥2) | เช็คสองครั้ง — **ก่อน start เป็นการเตือน** (บาง controller ยังไม่ resolve จนกว่า container จะมี) · **หลัง start เป็นตัวตัดสิน → ทิ้งเซลล์ + stop ทันที** · NCCL ตกไป TCP แล้วยัง serve ได้เงียบ ๆ `/health` ก็ผ่าน แต่ footprint คนละเรื่อง (`RUNBOOK` §5) |
| log ไม่มีบรรทัด `Available KV cache memory:` | เซลล์ไม่มีค่าวัดหลัก → `INVALID` · **ห้ามถอยไปใช้จำนวน token** |
| idle drift > 2.0 GiB | `INVALID` |
| รอบที่นับได้ < 3 ต่อ arm | `INVALID` |
| boot ตาย | **เก็บ log ไว้ใน `raw/` พร้อมเหตุผล** ไม่เอาไปเฉลี่ย (§1.9: เราทิ้งหลักฐานของ boot ที่ล้มเหลวทุกครั้ง) |

## 5 · เกณฑ์ตัดสิน — **เขียนไว้ก่อนรัน**

เกณฑ์ชุดนี้อยู่เป็นโค้ดใน `scripts/gpu_util_rank_probe.py` (`derive_verdict()` + ค่าคงที่หัวไฟล์)
**ตั้งใจให้เป็นโค้ด** เพื่อให้ diff ได้ว่าเกณฑ์ไม่ได้ถูกขยับหลังเห็นผล · และให้ใครก็ได้
re-derive จาก `results.json` โดยไม่ต้องรันฟลีตซ้ำ:

```bash
python3 scripts/gpu_util_rank_probe.py verdict --results <dir>/results.json
```

นิยาม: `dX_rank = median X(D2) − median X(D1)` · `dX_ckpt = median X(M1) − median X(D1)`

| verdict | เงื่อนไข | แปลว่า |
|---|---|---|
| **R** — กฎ rank ถูก | `dX_rank ≥ 2.0 GiB` **และ** ช่วงไม่ทับกัน (`min D2 > max D1`) **และ** `dX_rank > dX_ckpt` | NCCL โตตาม rank จริงในช่วง N=1..2 · **"0.75 ที่ TP8" มีกลไกรองรับ** · README ที่ต้องหาหลักฐานคือฝั่ง 0.80 · `fit` ได้พจน์ที่สเกลตาม rank |
| **C** — กฎ checkpoint ถูก | `dX_ckpt ≥ 5.0 GiB` **และ** `dX_ckpt ≥ 2 × dX_rank` **และ** `min M1 > max D1` | **README ทั้งสองถูกทั้งคู่ สำหรับ checkpoint ของตัวเอง** · การที่ทั้งคู่เป็น TP8 เป็นเรื่องบังเอิญ · `fit` **ต้องไม่ใส่** พจน์ NCCL ตาม rank — ต้องใส่ host-footprint ต่อ checkpoint แทน · ถ้า `private_dirty_gib ≥ 15` ด้วย = ยืนยันกลไก COW break ของ R8 |
| **H** — กฎ host-headroom ถูก **และทั้งสองเลขเป็นผลพลอยได้** | `X ≥ 8.0 GiB` ทุก arm **และ** ช่วง median ทั้งหมดต่างกัน `< 2.0 GiB` | `X` ใหญ่แต่ไม่ขึ้นกับทั้ง N และ checkpoint · 0.75 กับ 0.80 คือ `(MemTotal − X − safety)/MemTotal` ของเครื่องที่ `X` ต่างกันนิดเดียว · `fit` ได้ **ค่า host reserve ที่วัดจริง** แทนค่าเดา และ **ไม่มีพจน์ rank** |
| **INCONCLUSIVE** | อย่างอื่นทั้งหมด | ช่วงทับกัน หรือ effect ไม่ถึงเกณฑ์ · ขั้นต่อไป: เพิ่ม `--repeats`, ขยายแกน checkpoint (MoE ที่ใหญ่กว่าเดิมที่ N=1) **ก่อน** จะไปเพิ่มจำนวนเครื่อง |
| **INVALID** | ตาราง §4 ข้อใดข้อหนึ่ง | ไม่รายงานตัวเลขเลย |

### การล้มข้ออ้างแบบตรง ๆ — ไม่ต้องเทียบกับอะไร

> **ถ้า `X(N=1) ≥ 15 GiB`** — ที่ N=1 **ไม่มี NCCL อยู่ในโปรเซสเลย** ฉะนั้น footprint นอกงบก้อนใหญ่
> **ไม่ใช่หลักฐานของ NCCL reserve ต่อ rank** และการยก "~24 GiB/rank" ให้ NCCL ก็ตกไป
> — ข้อนี้ **Phase 0 เครื่องเดียวตัดสินได้**
>
> **ถ้า `X(2) − X(1) < 1 GiB`** — NCCL reserve เล็ก · ค่า `STACKED_COMM_BUFFER_GB_PER_NODE = 3.0`
> ที่ใช้อยู่ **สูงเกินจริง** และการเปลี่ยนไปเป็น 24×N จะทำให้ `fit` ปฏิเสธงานที่รันได้จริง

## 6 · ผลไหลกลับเข้า `fit` ยังไง

สคริปต์เขียน **`fit-input.json`** ที่ชื่อฟิลด์ตรงกับค่าคงที่ที่มันจะไปแทน — ไม่ต้องแปลอีกชั้น:

```
MemTotal = idle_used  +  gpu_util × MemTotal  +  X  +  MemAvailable(serving)
           ─────────     ──────────────────      ─     ─────────────────────
           ค่าที่ fit เรียกว่า                    ค่าที่ fit เรียกว่า      safety margin
           UNIFIED_OS_RESERVE_GB               STACKED_COMM_BUFFER_    ที่ต้องรอดตอน peak
           (analyzer.py:50 = 12.0 เดา)         GB_PER_NODE
                                               (analyzer.py:60 = 3.0)
```

| ฟิลด์ใน `fit-input.json` | ไปแทนอะไร | ตอนนี้เป็น |
|---|---|---|
| `UNIFIED_OS_RESERVE_GB_measured` | `src/lmds/fit/analyzer.py:50` | `12.0` — เดาไว้ ไม่เคยวัด |
| `STACKED_COMM_BUFFER_GB_PER_NODE_measured` (= `dx_rank_gib`) | `src/lmds/fit/analyzer.py:60` | `3.0` — คอมเมนต์เขียนว่า "เผื่อจากที่วัดบน 2×Spark ~2–3 GB/rank" · **การวัดนี้ยืนยันหรือล้มมันตรง ๆ** |
| `STACKED_COMM_BUFFER_valid_for_node_counts` | `[1, 2]` | ขอบเขตที่ห้ามอ้างเกิน |
| `checkpoint_host_footprint_gib` (= `dx_ckpt_gib`) | **พจน์ใหม่** ที่ยังไม่มีใน `fit` | ถ้า verdict = C นี่คือของที่ต้องเพิ่ม ไม่ใช่พจน์ rank |
| `x_at_n1_gib` | หลักฐานล้มข้ออ้าง "24 GiB/rank = NCCL" | — |
| `kv_read_from` | ยืนยันว่าอ่าน **GiB** ไม่ใช่ token — `sizing.py` ยังอ่าน `measured["kv_cache_tokens"]` อยู่ (§1.6 ยังไม่แก้) | — |
| `extrapolation_do_not_treat_as_measured` | ค่า N=4 / N=8 **ที่เป็นการคาดการณ์** | ติดป้ายไว้ในไฟล์เอง |

> **ทีม fit-fix ถือ `src/lmds/fit/*` อยู่ — โปรโตคอลนี้ไม่แตะโค้ดนั้น** ส่งเป็น `fit-input.json`
> ให้เขาเอาไปใช้ · และข้อที่ควรบอกเขาก่อนเลย: **อย่าเพิ่งเปลี่ยน `STACKED_COMM_BUFFER_GB_PER_NODE`
> เป็นพจน์ที่สเกลตาม rank จนกว่าจะมีผล** — ถ้า verdict ออกมาเป็น C หรือ H การเปลี่ยนนั้นคือ
> การเข้ารหัสสมมติฐานที่ผิดลงไปในสินค้า และมันจะดูน่าเชื่อถือกว่าเดิมทั้งที่ผิดกว่าเดิม

## 8 · สิ่งที่การวัดนี้ **ไม่ตอบ**

ขอบเขตที่ซื่อสัตย์มีค่ากว่าการอ้างเกินจริง · รายการนี้ต้องถูกคัดลอกเข้า `README.md` ของ artifact ทุกครั้ง:

1. **ไม่ตอบอะไรเลยเกี่ยวกับ N=4 หรือ N=8** — สองจุด (N=1, N=2) พิสูจน์ความเป็นเส้นตรงไม่ได้ และ NCCL
   **เปลี่ยนรูปเมื่อเกิน 2 rank** (ring/tree, channel เพิ่ม, routing ข้าม cage) · ตัวเลข N=8 ที่สคริปต์พิมพ์
   ติดป้าย `extrapolation_do_not_treat_as_measured` ไว้แล้ว · **ห้ามเขียนเป็น `validated_on` ใน catalog**
2. **ไม่ตอบว่า DeepSeek-V4.1-Flash หรือ GLM-5.3 ควรตั้งเท่าไร** — เราไม่ได้รันทั้งคู่ และรันไม่ได้ ·
   สิ่งที่ได้คือ *กลไก* ที่อธิบายว่าทำไมสองรีโปรายงานคนละเลข ไม่ใช่เลขของสองรีโปนั้น
3. **ไม่แตะ regime ที่ข้ออ้าง 0.75 เกิดขึ้น** — prefill 500K–900K ที่ head เหลือ 1.1–1.4 GiB ·
   นั่นต้องใช้โมเดลใหญ่ + context ยาว + 8 เครื่อง · **peak headroom ที่เราวัดคือ peak ของ arm เรา ไม่ใช่ของ regime นั้น**
4. **ไม่ตอบเรื่อง bandwidth / HCA** — นั่นคือ WS-1.2 · `docs/HCA-DUAL-TEST.md` + `scripts/hca_ab_bench.py`
5. **ไม่ตอบเรื่อง EXL3 · virtual heads · TP3** — คนละ loader คนละสมมติฐาน
6. **ผลผูกกับเครื่องคู่ที่ใช้** — `idle_used` รวม OS/docker/page-cache ของไซต์นั้น · เราจึงรายงาน
   `X` (ค่าสุทธิหลังหัก idle) **คู่กับ** `idle_used` เสมอ · เอาไปใช้กับเครื่องที่ตั้งค่าต่างกันไม่ได้ตรง ๆ
7. **ไม่ตอบอะไรเกี่ยวกับฮาร์ดแวร์ที่ไม่ใช่ GB10**
8. **`private_dirty_gib` เป็นหลักฐานสนับสนุน ไม่ใช่ตัวตัดสิน** — มันชี้ไปทาง COW break ได้ แต่ไม่ได้
   พิสูจน์ว่า mapping ตัวไหนถูก break · การพิสูจน์นั้นต้อง `/proc/<pid>/smaps` รายชิ้น ซึ่งอยู่นอกขอบเขตนี้

## 9 · Artifact — ของดิบต้องไปอยู่ที่ไหน

```
docs/evidence/gpu-util-rank/<UTC-yyyy-mm-dd>-<nodes>/
├── README.md          # verdict + ตาราง + §8 คัดลอกมาทั้งท่อน

├── fit-input.json     # ส่งต่อทีม fit-fix ตรง ๆ (§6)

└── raw/
    ├── <arm>-rep<N>-<node>-engine.log     # log ดิบทุก rank
    ├── <arm>-rep<N>-<node>-{pre,steady}.json
    ├── <arm>-rep<N>-<node>-watch.txt      # peak headroom ตอน load
```
