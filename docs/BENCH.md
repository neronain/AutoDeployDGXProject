# ให้คะแนนโมเดล — `lmds bench`

วัด **โมเดลที่รันอยู่จริง** ผ่าน OpenAI API: quant ตัวที่คุณรัน บนเครื่องที่คุณมี ด้วย engine
build ที่คุณติดตั้ง — สามอย่างที่เปลี่ยนผลมากที่สุดและไม่มีอยู่ในตัวเลขบนหน้าโมเดลของ
Hugging Face

## ทำไมไม่ใช้ `bench` ของ controller

คำสั่ง `bench` มีไม่ครบทุก engine และวัดคนละวิธี ตัวเลขจึงเทียบข้าม engine ไม่ได้ ซึ่งเป็นเรื่องเดียวที่คนอยากทำกับหน้าคะแนน

ตั้งแต่ 0.6.0 controller ของ **vLLM เดี่ยวและ stacked** มี `bench` / `stress` จริง (เดิมมีแต่ชื่อใน allowlist ของหน้าเว็บ
ไม่มีตัวจริงใน template ไหนเลย) — llama.cpp และ SGLang ยังไม่มี · ใช้เป็น "ดูเร็ว ๆ ว่าเซิร์ฟเวอร์นี้ตอบเร็วแค่ไหน" ไม่ใช่คะแนน:

| คำสั่ง | ค่าตั้งต้น | พิมพ์อะไร |
|---|---|---|
| `bench [RUNS] [TOKENS]` | 3 รอบ × 256 tokens | ต่อรอบ: `ttft` · จำนวน token · เวลารวม · tok/s รวม · **decode tok/s** ((tokens−1)/(total−ttft)) · สรุป **median** ttft / tok/s |
| `stress [REQUESTS] [CONC]` | 16 คำขอ × 4 สาย | `ok N/total` · latency **p50 / p95 / max** · จำนวนที่ล้ม — ตอบว่า `max-num-seqs` ที่ตั้งไว้รับได้จริงไหม |

ทั้งคู่ยิง head ที่ `127.0.0.1:<port>` ผ่าน API จริง (stream) — stacked ไม่ต้องมี `cluster.env` · จากหน้าเว็บ: ปุ่ม **bench** /
**stress** ในหมวด tests (งานยาว รันเป็น job ยกเลิกได้) · จาก hub: `lmds node ctl <เครื่อง> <slug> bench 5 512`

**โมเดล embedding ไม่มีคะแนน** — `lmds bench` วัดโมเดล chat (tool calling · JSON · ภาษาไทย · reasoning · vision ฯลฯ) ·
โมเดล embedding พิสูจน์ด้วย `./<slug>-single.sh test-embed` (ยิง `/v1/embeddings` 3 ประโยค คู่ไทย↔อังกฤษความหมายเดียวกัน
ต้องได้ cosine สูงกว่าประโยคที่ไม่เกี่ยว — vector ที่ pooling ผิดดูปกติทุกอย่างยกเว้นข้อนี้) ดู [USAGE §4.9](USAGE.md)

## ไม่มี "คะแนนความฉลาด"

เครื่องมืออย่าง Local-Bench แปะค่า IQ จาก Artificial Analysis ซึ่งเป็นดัชนีของ **โมเดลต้นทาง**
ไม่ใช่ของ quant ที่รันอยู่จริง · เอามาแปะแล้วมันจะดูเหมือนเราวัดเอง ทั้งที่ไม่ได้วัด
ที่นี่ให้คะแนนสองแกนที่วัดได้จริงเท่านั้น: **ความเร็ว** กับ **ความสามารถ**

## เปิดดูตรงไหน

**คอนโซล** (0.6) → เมนูซ้าย **Library → Scores** (`#/scores`) แล้วกด **Show** — เดิมอยู่ใต้ "Models on this machine"
ในหน้าเดียวยาว ๆ

ตารางนี้รวม **ทุกเครื่องในฟลีต** ไม่ใช่แค่เครื่องที่คอนโซลนั่งอยู่ — hub ถาม node ทุกตัว
ผ่าน SSH ตอนกด Show · เครื่องที่ถามไม่ได้ขึ้นเป็นบรรทัดเตือน ไม่ใช่หายไปเงียบ ๆ

**ดูรายละเอียดเพื่อนำเสนอ** — ปุ่ม **Details** ท้ายแถวในตารางคะแนน เปิดหน้าที่แสดง
ทุกงานเป็นแท่งเทียบกัน: decode / prefill / TTFT พร้อมแถบสรุปด้านบน (เครื่องที่รัน, โมเดล,
quantization, decode เฉลี่ย, จำนวนงาน, context สูงสุด) และการ์ดรายงานต่อหนึ่งงาน ·
ทำมาให้ถ่ายหน้าจอไปใส่สไลด์ได้เลย (สั่งพิมพ์ก็ซ่อนปุ่มให้เอง)

**ลบผลที่ไม่ต้องการ** — ปุ่ม **Delete** ท้ายแถว ลบผลของโมเดลนั้นทั้งหมด (ไฟล์อยู่ที่เครื่อง
ที่วัด ระบบส่งคำสั่งไปลบให้เอง) · จาก CLI: `lmds bench remove <slug> [--keep-last N]`
ผลสะสมเร็วกว่าที่คิดเพราะการวัดซ้ำเป็นเรื่องปกติ

**พับหมวดได้** — ปุ่ม `−`/`+` หน้าหัวข้อ **Model scores** และ **Models on this machine**
· สถานะถูกจำไว้ ไม่กางกลับเองตอนรีเฟรช

**สั่งวัดจากหน้าเว็บ**

| โมเดลอยู่ที่ | กดตรงไหน |
|---|---|
| เครื่องที่คอนโซลรันอยู่ | ปุ่ม **Manage** ของโมเดล → ปุ่ม **Score** |
| เครื่องอื่นในฟลีต | ปุ่ม **⋯** ที่แถวของโมเดลในการ์ดเครื่องนั้น (หรือหน้าเครื่องจาก rail) → **Score** |

วัดได้เฉพาะโมเดลที่ **กำลังรันอยู่** · ผลถูกเก็บไว้ที่เครื่องที่รันโมเดลนั้น แล้ว hub ดึงมารวม (`lmds agent bench`)

## ใช้งาน

```bash
lmds bench run <slug>                 # ชุดเต็ม: 6 งาน + ความสามารถ 7 ข้อ
lmds bench run <slug> --quick         # 2 งาน — ดูคร่าว ๆ ไม่ใช่ตัวเลขที่เอาไปเทียบ
lmds bench run <slug> --caps-only     # ข้ามความเร็ว
lmds bench run <slug> --runs 5        # ยิงกี่รอบต่องาน แล้วเอาค่ากลาง (ค่าเริ่มต้น 3)
lmds bench list                       # ตารางคะแนนของทุกโมเดลที่เคยวัด
lmds bench show <slug>                # ผลละเอียดรอบล่าสุด
lmds bench show <slug> --history      # ทุกรอบ — ใช้เทียบก่อน/หลังอัปเกรด engine
lmds bench remove <slug>              # ลบผลที่เก็บไว้ทั้งหมดของโมเดลนี้
lmds bench remove <slug> --keep-last 1 # เก็บรอบล่าสุดไว้รอบเดียว
```

บนคอนโซล: **Library → Scores** ในเมนูซ้าย · ปุ่มวัดอยู่ในแผง **Manage** ของโมเดลที่รันอยู่

## ความเร็ว — วัดยังไง

| ค่า | ความหมาย |
|---|---|
| TTFT | ตั้งแต่ส่งคำขอจนได้ token แรก (รวม queue + prefill) |
| decode tok/s | (token ที่ได้ − 1) ÷ เวลาตั้งแต่ token แรกถึงตัวสุดท้าย |
| prefill tok/s | prompt_tokens ÷ TTFT — ค่าประมาณ มี queue ปนอยู่ |

- **ลบ 1 จาก token** เพราะตัวแรกถูกนับไปแล้วใน TTFT ไม่ลบจะได้ตัวเลขสูงเกินจริง
- **นับ `reasoning_content` เป็น token ที่ decode ด้วย** ไม่งั้นโมเดลสาย reasoning ดูช้ากว่าความจริงมาก
- **median ไม่ใช่ mean** รอบแรกมักช้ากว่า ค่าเฉลี่ยจะถูกมันดึงลงทั้งชุด
- **ยิงรอบอุ่นเครื่องทิ้งหนึ่งครั้ง** ต่อหนึ่งงาน
- **ทำลาย prompt cache ทุกรอบ** ด้วย nonce ที่หัว prompt · ถ้ายังมี `cached_tokens` เหลือ
  เกิน 10% ระบบจะเตือนว่าตัวเลข TTFT/prefill รอบนั้นเชื่อไม่ได้

ชุดงานไล่ context 512 → 8K เพราะ decode ตกตามความยาว context อย่างชัดเจน — วัดที่ 512
แล้วบอกว่า "เร็วกว่า" ทั้งที่อีกตัววัดที่ 8K คือการเทียบคนละเรื่อง · งานที่ยาวเกิน context
ของโมเดลถูกตัดออก ไม่ใช่ปล่อยให้สอบตก

## ความสามารถ — 7 ข้อ

| ข้อ | น้ำหนัก | ผ่านเมื่อ |
|---|---|---|
| ทำตามคำสั่ง | 2 | ตอบคำเดียวตามที่สั่ง |
| tool calling | 3 | ออกมาในฟิลด์ `tool_calls` จริง **ไม่รับการพิมพ์ JSON ลง content** |
| JSON structured output | 2 | `response_format: json_object` แล้ว parse ได้ |
| ตอบภาษาไทย | 2 | ถามไทยแล้วตอบไทย |
| จำ context ยาว | 2 | หาเข็มที่ซ่อนกลางข้อความยาวเจอ |
| แยก reasoning | 1 | มี `reasoning_content` แยกจาก `content` |
| รับภาพ | 1 | บอกสีของภาพทดสอบถูก |

ทุกข้อวัดจาก **พฤติกรรมจริงที่ปลายทาง** ไม่ใช่จากที่ `MODEL_PROFILE.yaml` จดไว้ — เพราะเคสที่
เจอบ่อยที่สุดคือ profile บอกว่ารองรับ แต่เซิร์ฟเวอร์ไม่ได้เปิด flag ที่ต้องใช้ (llama.cpp ที่ลืม
`--jinja` → tool calling ตายเงียบ ๆ)

ข้อที่ **ข้าม** (เช่น vision บนโมเดลที่ไม่มี mmproj) ไม่ถูกนับในตัวหาร ไม่ใช่นับเป็นสอบตก ·
คะแนนรวมมาพร้อมรายชื่อข้อที่ตกเสมอ เพราะ 85/100 ที่ตก tool calling ใช้กับ agent ไม่ได้เลย
ส่วน 85 ที่ตก vision อาจไม่เกี่ยวกับงานที่จะเอาไปใช้

### โมเดลที่คิดนาน

โมเดลสาย reasoning ใช้ token ไปกับการคิดก่อนตอบ · ถ้างบหมดก่อนตอบ ระบบ **ลองซ้ำด้วยงบ
สามเท่า** แล้วค่อยตัดสิน และแยกข้อความ "ตอบผิด" ออกจาก "ไม่ทันได้ตอบ" เสมอ

เคสที่พบจริง: `json_object` ของ llama.cpp บังคับ grammar ตั้งแต่ token แรก ความคิดของโมเดล
จึงต้องเป็น JSON ไปด้วย แล้วมันวนอยู่อย่างนั้น — ไม่ใช่ว่าโมเดลทำ structured output ไม่ได้
แต่ทำพร้อมกับคิดก่อนตอบไม่ได้ · ระบบจะบอกเหตุนี้ในช่องผลลัพธ์

## ผลถูกเก็บไว้ที่ไหน

`~/.lmds/bench/<slug>/<เวลา>.json` — หนึ่งไฟล์ต่อหนึ่งรอบ อ่านด้วยตาได้ ก๊อปข้ามเครื่องได้
แต่ละไฟล์เก็บสเปกเครื่อง + engine build + quant + context ไว้ด้วย เพราะ "32 tok/s" โดด ๆ
ไม่มีความหมายถ้าไม่รู้ว่าวัดบนอะไร

ตารางคะแนนเอา **รอบล่าสุดของแต่ละโมเดล** แต่ถ้ารอบล่าสุดเป็น `--caps-only` (ไม่มีข้อมูล
ความเร็ว) จะยืมตัวเลขความเร็วจากรอบก่อนมาแสดงพร้อมตราเวลาของมันเอง — ไม่ใช่ปล่อยให้
คอลัมน์กลายเป็นขีดกลางทั้งแถว
